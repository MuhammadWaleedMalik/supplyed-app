# Authentication, onboarding and account audit

Audit date: 20 October 2026. Scope: mobile source, corresponding website flows and backend controllers/services/repositories/schema. This is a source and mocked verification report, not a production-readiness claim.

The backend contains real data and has a running watcher. No authentication requests, OTP sends, account creation, database changes, server restarts or deployments were performed. Backend fixes are staged in [account-security.patch](backend-fixes/account-security.patch) and [session-rotation.patch](backend-fixes/session-rotation.patch). They have only been applied to an isolated copy under `android/app/build/audit/backend`. Website and mobile logout companions are also staged separately. The live source and service still have the findings below. The session patch has a hard website compatibility gate; see [rollout notes](backend-fixes/session-rotation-README.md).

## Implemented mobile corrections

- Dropdown sheets now virtualize large collections, search, show no-match states, respect safe areas/keyboard and provide multi-select count/Done/limit. Failed dropdown GETs no longer trigger an invalidation loop. Subject/skill aliases follow website/backend punctuation and ampersand normalization. Earlier read-only inventory found 3,844 city choices, 337 skills and 251 regions; rendering every option explained the apparent dropdown freeze.
- `utils/api/request.ts` refreshes and replays only `ACCESS_TOKEN_EXPIRED`. Domain 401 errors such as incorrect 2FA no longer refresh/replay a mutation or log out the user. Invalid/missing access-token codes still expire the session.
- Onboarding validates the website’s form requirements before account/profile writes and gives an explicit error summary. Verified phone values are preserved. TRN was removed from the form/review because the backend has no writable TRN field; collecting it previously discarded the value.
- Signatory request failures are recoverable in Documents. Approval status and current profile state are checked again before submission/navigation. Rejected/deactivated profiles can be explicitly resubmitted through Documents; other unsupported states produce an error.
- Settings sends `null` for cleared nullable fields; `undefined` had disappeared from JSON and silently retained old values. Account and Profile saves are isolated, with no hidden-field validation trap.
- Phone verification uses the successful verification response directly. 2FA enable/regenerate retains recovery codes from the successful response, avoiding a follow-up read failure that previously hid the only copy.
- Settings, documents, onboarding, phone and review async completions check mounted/session state before updating UI or continuing the next operation. Document preview does not open an old account’s signed URL after the session changes.

Website comparison sources included `features/onboarding/validation.ts`, `features/onboarding/schemas.ts`, `features/onboarding/use-onboarding.ts`, `features/settings/validation.ts`, `features/settings/use-settings.ts`, `lib/uk-validation.ts`, and its authentication/profile/document flow documentation. Backend DTOs, service validation and schema were checked as the persistence authority.

## Backend defects and staged corrections

Paths below are relative to `supplyed-backend`; line references describe the original source inspected.

| Finding | Evidence | Staged correction |
| --- | --- | --- |
| Any signed-in user could request another account’s private email/phone/security details | `src/modules/users/users.controller.ts:81` GET `:id` had no self/admin authorization | UUID validation plus self/admin check before fetching the private DTO. |
| Verified phone could be changed through generic account PATCH or a new-number OTP | `users.service.ts` generic `update`; `phone-verification.service.ts` only rejected the same verified number | Separate owner-update method; E.164 comparison; conditional update matching previous phone/verification state; OTP send/claim rejects verified accounts. Admin API remains an explicit separate route. |
| Null passed optional DTO validation, then could reach string operations | `users/dto/update-user.dto.ts` used IsOptional | ValidateIf only skips undefined; IsString rejects null. |
| Email/phone/reset OTPs could be reused concurrently after bcrypt comparison | `auth.service.ts:175`, `:231`; `phone-verification.service.ts` verify path | Conditional claim requires matching user/id, unconsumed, unexpired and attempts below limit. Claim and corresponding User update share one transaction. |
| Concurrent sends could bypass resend throttle or leave multiple active codes | OTP repository create methods; phone service read-then-send throttle | Per-user PostgreSQL row lock serializes send and claim; throttle checks, invalidation and insert are inside one transaction. Email/reset gain configurable cooldown/hour limits. |
| Failed concurrent guesses could race attempt accounting | Three OTP repositories incremented/consumed in separate operations | Conditional increment caps attempts on the still-active record. Expired/consumed/exhausted codes cannot be claimed. |
| Re-registering an unverified email changed password/role before code issuance succeeded | `auth.service.ts` existing-user register branch | Signup password/role update is in the code-issuance transaction after throttle/verified-state checks. A throttled retry leaves previous credentials unchanged. |
| Forgot-password throttling could disclose account existence | New reset throttle affects existing users only | Resend-limit exception is suppressed for this generic response; no mail is sent for a throttled or unknown account. |
| Verifying email could create a session without checking already-enabled 2FA | `auth.service.ts` email verification returned createLoginResponse directly | Reuses createAuthenticatedResponse, with mobile challenge handling added. |
| Concurrent 2FA setup replacement could enable a different secret | `two-factor.repository.ts` enable matched user + disabled state only | Compare the exact encrypted secret that was verified in the conditional update. |
| Concurrent use/regeneration of recovery codes could restore a consumed code from a stale list | `two-factor.repository.ts` completeChallengeWithRecoveryCode | Match the complete expected recovery-hash list before replacing it; mismatch rolls back challenge consumption. |

The account-security password-reset transaction also revokes persisted RefreshToken records. Alone, it cannot revoke tokens from the current stateless server. The separate session patch makes issuance/rotation use those records and additionally invalidates outstanding 2FA challenges.

The session patch stores only SHA-256 token hashes, rotates the hash conditionally on a stable session row, rejects legacy tokens without session claims, and adds signature-verified logout. New password-authenticated sessions and 2FA challenge creation/reuse compare the observed password hash under the same user lock used by password reset. Thus an old-password login cannot obtain a new surviving session or challenge after a reset wins the race. Password hashes are never added to JWTs or returned DTOs.

## Remaining issues and verification limits

1. **High in the running server: refresh/session revocation is still absent.** `auth.service.ts:109` verifies a stateless refresh JWT and `:296` signs another; `prisma/schema.prisma:324` has an unused RefreshToken model. The running server has no logout route. The separate staged session patch addresses persistence, rotation, logout and reset races, but is not deployed. The separate mobile logout companion is also unapplied. **Do not deploy session rotation until the website refresh-cookie gate below is resolved.**
2. **Required-document readiness has a separate verified staged correction.** The running `instructors.service.ts:245` and `institutions.service.ts:187` still permit owner submission without document checks. [profile-document-submission.patch](backend-fixes/profile-document-submission.patch) now checks current active requirements and newest owned profile uploads in the status transaction, following existing website policy and preserving admin behavior. Its 23 mocked assertions and combined isolated compile passed; real PostgreSQL relation/concurrency behavior remains unverified. The patch remains unapplied to the real server.
3. **Auth abuse controls remain incomplete.** Per-account OTP send/claim protections are staged. Password-login and security-settings attempt policies still need a coordinated server/gateway rate limit, with non-enumerating errors. No brute-force traffic was generated.
4. **Production configuration requires separate review.** Weak JWT secret fallbacks and raw token-bearing URL logging were identified. The integration agent owns a separate staged production-configuration patch applied after account-security; the real service remains unchanged.
5. **Real device/provider verification is outstanding.** No phone was available. Native dropdown layout, large text/keyboard, iOS, Google provider exchange, email delivery, SMS code entry, keychain persistence after OS termination, image/document picker and actual S3 upload/download were not exercised here.
6. No live account was created, updated, verified, disabled or logged out. No real document, trust approval, notification preference, payout setting or recovery code was changed. Matched source flows and mocks are not a substitute for a later controlled account/device acceptance test.
7. **Website email-verification compatibility is now staged:** [web-email-two-factor.patch](backend-fixes/web-email-two-factor.patch) reuses the existing challenge normalizer/action and `TwoFactorChallengePage` for both Login and Signup, and prevents the legacy credentials branch from accepting a challenge as a session. Apply it with account-security; the real website is unchanged.
8. **Hard session rollout gate:** website `lib/server/token-refresh.ts` can refresh during a Server Component request when it cannot persist cookies; it relies on a process-local 30-second grace cache. Strict backend rotation will invalidate that old cookie. Later requests, another worker, or concurrent workers can receive 401 despite a valid newly rotated token existing elsewhere. This requires coordinated refresh in a writable server endpoint and durable/shared session-token persistence or equivalent distributed coordination. No broad website session-store rewrite was attempted.
9. **Deliberate session limits:** legacy refresh tokens require a new sign-in at rollout. Lost refresh responses, lost secure-storage writes, or duplicate refreshes outside the client’s single-flight request can require sign-in. Rejected stale-token reuse does not revoke the latest successor automatically. Existing access JWTs remain valid until configured expiry (15 minutes by default). Offline local logout cannot guarantee server revocation.

## Staged refresh/logout implementation and rollout

The existing RefreshToken columns (`id`, `userId`, unique `tokenHash`, `expiresAt`, `revokedAt`) support the staged implementation without a database migration:

1. Each refresh JWT has a stable signed session ID and a unique `jti`; only its SHA-256 hash and expiry are persisted.
2. Refresh verifies signature/type/user/2FA and active hash. A conditional transaction replaces that session row’s current hash and expiry. Concurrent use of the old hash has one winner. No indefinite legacy bypass or replay grace is present.
3. Logout verifies the refresh JWT and revokes the signed session ID for its signed user. This also catches a refresh that rotated while logout was in flight. Password reset revokes all existing rows and deletes 2FA challenges while holding the user lock.
4. The staged mobile companion captures the old refresh token, clears local state immediately, and makes a public logout request with that captured token. A late failure cannot clear a newer account’s session. It is not applied while the running server lacks the endpoint.
5. Apply website email/2FA parity before account-security deployment; apply backend account-security and production-configuration patches before the session patch. Hold the session patch until the website writable/distributed refresh gate is resolved. Announce the explicit legacy-session sign-in cutoff when rollout is scheduled.

Backend patches must be applied during a controlled maintenance/release window, after reviewing all staged patches and running isolated tests. Applying source changes while the present watcher is active could change the live real-data service.
